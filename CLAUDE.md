# Battle City (NES) — verified C reconstruction

## Goal

Dissect the original ROM into a C-like reconstruction with **verification**,
so that a later agent can build a faithful reimplementation from it. Faithful
means: same RAM state, same PPU/APU register traffic and same controller
handling, frame by frame, for the same inputs. The deliverables are the C
sources and the documentation. The verification evidence is what makes them
trustworthy.

## Target identity (observed)

- `BattleCity (Japan) (En).nes`, 24592 bytes,
  sha256 `166ec235b062aa337045832843e2916f96f12dcf08972ad747016dbe77db761c`
- NES 2.0 header `4E 45 53 1A 01 01 00 08 ...`: mapper 0 (NROM-128),
  16 KiB PRG ×1, 8 KiB CHR ×1, horizontal mirroring (flags6 = $00). Verified:
  the title screen draws into $2800 and clears $2000, which only works with
  horizontal mirroring.
- PRG sha256 `040c74abfdf70f6eecf410651fc0a143ecab3967e321ff5793ca698aa3009d1e`,
  mapped at `$C000–$FFFF` (mirrored at `$8000–$BFFF`).
- CHR sha256 `a5d5a10b0fbe9b1a8b8806a06af2634d25ed993b3659131d01acdf86de9c00e9`,
  PPU `$0000–$1FFF`. These two hashes (not the file hash) identify a usable
  dump; headers differ between dumps.
- Vectors: NMI `$D400`, RESET `$C070`, IRQ/BRK `$C070`.
- `$C000–$C06F` is ASCII, not code: "COPYRIGHT 1981 1985 NAMCO LTD. ALL
  RIGHTS RESERVED" plus staff names. The reset code starts at `$C070` with
  `SEI; LDA #$10; STA $2000; CLD; ...` (wait-for-vblank loops).
- NMI `$D400` (first look): it saves registers, does OAM DMA from page `$02`,
  reads `$2002`, calls `$D8FD`, conditionally calls `$D50E` (if `$4D` is
  negative), sets PPUCTRL from `$50|$B0`, sets scroll from `$4F`, sets PPUMASK
  to `$1E`, calls `$D689`, `$DA93` and `$EA7E`, increments the frame counter
  `$0B` (and `$0A` every 64 frames), then RTI.

## ROM policy

The project contains no game data and never commits any. Everything that
needs the original bytes loads the user's own `.nes` at run time and checks
the PRG and CHR SHA-256 above; any other dump is rejected with a message.

- C: `re/src/rom.c` `bc_rom_load()` fills `PRG[]` (machine.h) and returns
  the CHR. The harnesses take the ROM path as their first argument.
- Python: `re/tools/rom.py` (`rom.prg()`, `rom.load()`).
- Default ROM, internally: `$BC_ROM` if set, else
  `battlecity/BattleCity (Japan) (En).nes` (`tools/rom.py`, `verify_all.sh`).
- Shipped game (planned): looks for `battlecity.nes` next to the executable
  (`BC_ROM_FILENAME` in `rom.h`).
- `re/rom/prg.bin`/`chr.bin` exist only for Ghidra/REA, which needs a raw
  PRG file: `python3 re/tools/rom.py --extract`. No build or tool reads them.
- Data tables become named views (address, length) into the loaded `PRG[]`,
  generated by a script. They are never copied into the source.
- `docs/battlecity.asm` reproduces the whole PRG (it reassembles
  byte-identical), so it is git-ignored and regenerated by `make listing`
  (`verify_all.sh` needs it).
  `src/mech/mech.c` holds only dispatch stubs since all routines are lifted.

## Verification method (non-negotiable)

1. **Oracle correctness.** Our `tools/emu` core is cross-checked against
   FCEUX 2.6.6 (source at `/d/Development/reverse/Software/fceux-2.6.6`,
   built headless as a test tool only; GPL, never copied into `src/`). The
   check: same ROM and same input script → identical per-frame RAM and
   identical register-write streams.
2. **Per-routine differential tests.** For every reconstructed routine, run
   the original 6502 code (from its entry until the matching RTS) and the C
   function from identical randomized/recorded states. Compare RAM, the
   relevant exit registers/flags, the ordered I/O log and the number of
   frames consumed. Frames pass only where the program waits for vblank
   (same model as lockstep; see `tools/harness/difftest.c`). Seed states
   from real gameplay snapshots, plus random fuzzing.
3. **Whole-game lockstep.** Run the C game (built against the same harness
   API) and the ROM side by side with recorded inputs. Diff per frame.
4. Record the results in `re/docs/verification.md`: which routines pass, how
   many cases, which states, and known gaps. Never claim "verified" without a
   test that ran and passed.

## Working with agents

- The user wants **Sonnet subagents** (`model: "sonnet"`) used for manual,
  parallelisable work: lifting batches of routines to readable C, writing
  per-routine docs, extracting tables. Spreading work across agents is
  explicitly allowed.
- Give each agent a self-contained package: its routine list, the relevant
  listing excerpt (`re/docs/battlecity.asm`), contracts (`re/docs/contracts.json`),
  the symbol status (`re/tools/symbols.py`), and the lifting guide
  (`re/docs/lifting_guide.md`). Each agent must make its routines pass
  `build/difftest` and `tools/verify_all.sh` before reporting back.
- Agents work on disjoint files (one `src/lifted/<module>.c` each) to avoid
  edit conflicts. The coordinator (main thread) merges the `.lifted` lists,
  `symbols.py` and the docs.
- Agents leave brief technical notes. When implementing or examining a routine,
  include a short summary of what was found and any useful references, such as
  assembly addresses, data tables, traces, or test results. Where helpful,
  mention assumptions, uncertain findings, unusual behavior, or implementation
  details worth revisiting. Keep notes concise and practical so the coordinator
  can review and integrate the work easily.

Since 2026-10-17 `battlecity/` is **not** a git repository. The git history
(and the pre-cleanup tree, ROM included) is kept in
`../battlecity_backup_2026-10-17/`. The tree is prepared for publishing:
`.gitignore` lists everything that is game data or generated from it (`*.nes`,
`re/rom/`, `re/docs/battlecity.asm`, `re/build/` with its screenshots,
audio dumps and save states). Such files may exist locally, but never move
them outside the ignored paths. If a new tool writes ROM-derived output,
add it to `.gitignore`. Where the ROM goes: README.md, "Where to put the ROM".

## Conventions

- Routine names: `sub_XXXX` until understood, then a descriptive name. Always
  keep the original address in a comment: `/* $D8FD */`.
- RAM variables: one global layout (`re/src/ram.h`) that mirrors the original
  addresses exactly, so tests can share memory images. Give a name to every
  address that is understood. Document each in `re/docs/ram_map.md` with how
  it is known (observed/derived).
- Hardware access in C goes through a thin HAL (`ppu_write`, `apu_write`,
  `pad_read`, `wait_vblank`, ...). The test harness implements the HAL by
  logging, so I/O order can be diffed.
- Preserve original quirks and bugs (8-bit wraparound, table overreads,
  off-by-ones). Note each one in a comment `QUIRK:`; do not "fix" them.
- Data tables (levels, graphics metadata, sound) are described by a script,
  not hand-typed: name, source address, length and element type, read
  from the loaded `PRG[]` (see ROM policy).
- Code/data separation must be justified: either reached by recursive
  disassembly from the vectors and jump tables, or executed in emulator
  coverage runs. Unreached bytes stay listed as unknown.

## REA session recipe

```
python3 re/tools/rom.py --extract        # writes re/rom/prg.bin if missing
open_binary path=/d/Development/reverse/rea-work/battlecity/re/rom/prg.bin
            format=raw-binary architecture=6502 entry_point=0xC000 provider_id=ghidra
```

Ghidra then auto-finds ~135 procedures. It does not seed RESET/NMI itself:
look at `$C070` and `$D400` explicitly. Annotations are lost on close, so
keep names in `re/tools/symbols` (to be created) and re-apply them with
`set_addresses_names`.

## Key facts learned (observed)

- Power-on RAM matters (RNG and counters read uninitialised RAM). All
  tools default to FCEUX's fill pattern; see `re/docs/verification.md`.
- NMI always lands in the wait loop at $D8F8/$D8FA (or NMI is disabled).
  The game never lags, so "main thread until wait, then NMI" is exact.
- Stack tricks: `pla pla` aborts in $C41D/$C7AB/$C9C0/$E972, and an inline
  jump table after `jsr $ECD0` (at $EBE3, 18 entries). There is a BIT-skip
  at $EC87.
- User docs (`battlecity/docs/*.md`) come from an earlier decomp attempt.
  They are a good source of names and behaviour, but must be re-verified.
